How data gets in

Four independent lanes, each one source → one collector → one file. Nothing shares a process and nothing shares a database — the join happens later, in whichever app reads the folder.

How data gets out

Five consumers read the same folder. Three of their four exits work; the one that carries the dashboards to the public web has been severed since April.

Why the factory feed goes stale

Two schedulers are configured for the same platform and they behave differently when the Mac is asleep. That single difference explains every gap in the data.

The nightly chain

One launchd job at 21:30 runs five steps in sequence via ~/Library/Scripts/MartBids/run_scraper.sh. Order matters here — each step consumes what the one before it wrote.

  1. martbids_scraper.py38 marts, per-animal detail and ICBF indices → sold_lots.csv
  2. lsl_scraper.py18 mart codes from the public catalogue → lsl_lots.csv
  3. fetch_weather.pyreads the mart × date pairs step 1 just wrote, fills them from Open-Meteo
  4. generate_report.pybuilds the PDF from steps 1–3 plus factory prices, emails 4 recipients
  5. git_push.pycommits and pushes the data files — fails here, every night

What needs fixing

Ranked by what it costs you today. The first two are why the platform looks stale from outside.

Nothing has reached GitHub since 24 April

Critical

git_push.py commits successfully then fails on push with Invalid username or token. Password authentication is not supported — every night, silently, because the launcher logs the failure and moves on. 89 commits are queued locally and Streamlit Cloud has been serving 24 April data for 105 days. Two token files exist and their contents differ; the one git_push.py reads lives at ~/Library/Scripts/MartBids/.github_token, not the one in the repo.

Fix → Mint a fresh fine-grained PAT (the current one is a legacy ghp_ classic token), write it to the ~/Library path, delete the stale repo copy, then push the backlog. Consider having the launcher surface a failure rather than swallow it.

The factory pipeline is scheduled where it cannot run

Critical

Both factory jobs are cron entries at 07:00 and 07:30 on Mondays and Thursdays. Cron does not replay missed runs, and this Mac is usually asleep at 7am — so they last fired on 18 June. Last night’s report carried the warning “factory price data 19 days old” for exactly this reason.

Fix → Move both scripts into the 21:30 run_scraper.sh chain, which launchd does replay on wake. Then delete the five crontab entries — every one of them duplicates something launchd already handles.

Factory prices would still not deploy after a token fix

High

git_push.py stages an explicit list of eight files and factory_prices_clean.csv is not among them — even though it is git-tracked and both dashboards read it. The factory tab on a restored Streamlit deployment would stay frozen at whatever was last committed by hand.

Fix → Add factory_prices_clean.csv to the list in git_push.py, and to run_scraper.sh’s inline copy while you are there.

All 50,947 Livestock-Live lots are labelled “LSL Auctions”

High

get_mart_name() reads the page’s <h1>, which on livestock-live.com is the site name rather than the mart’s. Every row from 18 distinct marts collapses to one label. The consequences are quiet but real: those lots map to region Other in bank_dashboard.py, so 21% of the combined dataset sits outside every provincial breakdown; they never match the weather join; and the model sees them as a single mart category.

Fix → The real identity is already captured in mart_code (M262, CORRIN, CAHIR …). Map code → name and backfill the existing rows — no re-scrape needed.

The price model is 112 days old

Medium

cattle_model.pkl was trained on 17 April against 54,447 lots. There are now 241,519 — 4.4× the training set, across a season the model has never seen. Test MAE was €0.44/kg at the time; nothing has measured it since, and nothing schedules a retrain.

Fix → Add train_model.py to the chain on a weekly cadence, and write each run’s metrics to a history file so drift is visible rather than inferred.

Two schedulers, two diverged copies of the same script

Medium

crontab and launchd both define this pipeline, and run_scraper.sh exists twice — once in the repo, once in ~/Library/Scripts/MartBids/. Only the ~/Library copy runs. They have drifted apart: the repo copy still does an inline git push reading a token path that no longer holds the live token, so anyone running the repo version gets a different and more confusing failure.

Fix → Keep launchd, drop cron. Make the ~/Library file a one-line shim that calls the repo script, so there is a single source of truth under version control.

MartBids credentials are committed in plaintext

Medium

martbids_scraper.py carries the account email and password as literals at the top of the file. The file is git-tracked and has been pushed to GitHub. .gitignore correctly excludes email_config.json and .github_token — this one was simply missed.

Fix → Move to environment variables or a gitignored config, rotate the MartBids password, and treat the credential as exposed in history regardless of the repo’s visibility.

The weekly Drive backup is erroring

Low

launchctl list reports exit status 78 for com.johnscanlan.martbids.backup, and backup.log last wrote on 27 July. Separately, the backup file list includes sold_lots.csv but not lsl_lots.csv — 50,947 lots that exist in no backup at all.

Fix → Run the script by hand to surface the real error (78 is usually a config or path problem), and add lsl_lots.csv to the list.

Dead code and leftovers

Low

In generate_report.py, page5_ml_metrics() and page2_breed_weight_table() are defined but never called; meta is loaded in main() and never used; and the docstring advertises five pages while main() builds four. Elsewhere: mart_soup is an abandoned Selenium prototype, MartIndex/ and Meetings - Notes/ are empty, and com.johnscanlan.martbids.test.plist still points at /tmp/test_launchd.sh.

Fix → Either wire the ML-metrics page back into the report — the model deserves a visible scorecard — or delete it and correct the docstring.

What is genuinely solid

Worth stating plainly, because the findings list above reads harsher than the system deserves.

The write path is careful in a way most side projects are not. Every append goes through data_utils.safe_append_csv: build the combined frame, write to a temp file in the same directory, re-read it, verify the row count matches, and only then atomically rename. A crash mid-write leaves the original file untouched. The Parquet conversion does the same, and the Drive backup writes to a dated folder so no previous day is ever overwritten. That is why 241,519 lots collected over five months have no corruption in them.

The de-duplication keys are well chosen too — val_code for lots, a five-part composite for factory prices — so re-running any scraper is free and safe, which is exactly the property you want when a schedule is unreliable. Today’s manual factory run added 13,233 genuinely new rows and re-derived cleanly, with no special handling required.
